## 0 · Approach identity and output
- **0.1 Team ★** — name, the one or two members (teams are at most two, unless a larger team was approved on request), affiliations, corresponding contact: team_19. One member: Ilia Sucholutsky, Assistant Professor of Computer Science, Purdue University (AITP Lab). Contact: isucholu@purdue.edu.
- **0.2 Plain-language summary ★** — one paragraph, what the approach does (not how): A single large language model reads the complete survey instrument and all sixteen intervention texts and writes down, as an explicit and inspectable parameter file, what it expects the human study to find: where each outcome sits in the control condition and how that differs by party, age, education, race, gender and income; how much each intervention moves trust in climate scientists, which facets of trust it moves, how far the effect carries to the secondary and tertiary outcomes, and how the effect differs across partisan groups. A deterministic simulator then draws 4,000 synthetic respondents and answers every scored survey item for each of them in every one of the 17 conditions, producing an individual-level dataset with realistic slider behaviour (integer responses, heaping, endpoint use, zero-inflated donations, rare newsletter signups). The predictions are the model's structured prior beliefs about US public opinion and about persuasion effects, not a per-respondent role-play.
- **0.3 Submission tier & approach family ★** — tier (1/2/3); family (e.g. per-respondent simulation / agent / direct forecast; single model / ensemble / multi-agent; zero-shot / literature-conditioned): Tier 1. Per-respondent simulation from an LLM-elicited explicit generative model; single model; zero-shot (no fine-tuning, no retrieval, no external data files in context).
- **0.4 Pipeline diagram** — ordered steps from raw inputs to submitted file: (1) Model reads `survey/questionnaire.txt`, `codebook.csv`, `survey/condition_codenames.csv`, the benchmark preregistration page and the template README. (2) Model writes `pipeline/priors.py`: census quota structure, party/education/income structure, three correlated latent traits, per-item control baselines (mean, Democrat−Republican gap, loadings, noise), per-intervention treatment-effect specification (base effect on the trust composite, subscale weights, partisan multipliers, outcome-specific overrides, spillover fractions), and response-style parameters. (3) `pipeline/simulate.py` (seed 20260831) draws 4,000 profiles, each with fixed random numbers, and generates raw item-level responses under all 17 conditions → `raw_data_deposit/team_19_raw_export.csv` (Qualtrics variable names and codes). (4) `pipeline/clean_py.py`, a line-for-line port of `scripts/lib/clean_lib.R`, applies the study's recodes and composites → `predictions/team_19_T1_primary_v1.csv`. (5) `pipeline/finalize.py` fingerprints the file, writes `.zenodo.json` and runs the structural checks mirrored from `scripts/lib/check_lib.R`.
- **0.5 Coverage ★** — number of respondents/cells/estimates; mapping to conditions. Full coverage is required: every submission predicts **all 16 interventions and all 13 outcomes** (partial coverage is not accepted). Confirm here: Confirmed. 68,000 synthetic respondent rows = 4,000 per condition × 17 conditions (control + all 16 interventions), all 13 outcomes plus the 12 trust items and 6 moderators on every row, no missing values.

- **A.2 Degree of automation ★** — confirm fully automated, no human in the loop at prediction time; note any exception: The human team member supplied no predictions, numbers, rankings or substantive guidance; his role was to point the model at the benchmark, ask it to build the submission using its own judgment rather than external model APIs, approve tool calls, and handle the GitHub/Zenodo deposit. Exception to note honestly: the parameter file was written by the model in one interactive Claude Code session rather than by a scripted, re-runnable API call, so "re-running the pipeline" reproduces the file from the parameters exactly (seeded), but re-eliciting the parameters would require a new model session. The model also inspected summary statistics of its own simulated output twice (party shares, control means, effect ordering) and adjusted parameters so the simulation matched what it had intended; those checks used only the synthetic data, never any human data.

## D · Persona / profile construction (Tiers 1–2)
- **D.1 Profile source** — source of demographic profiles you constructed: a public survey (e.g. GSS / ANES / Census), other survey, fully synthetic, or none. The benchmark ships no participant pool; report how you built yours, incl. condition assignments: Fully synthetic. Gender × age and gender × race/ethnicity drawn from the census cross-quota table in the benchmark preregistration; education, income and party drawn from model-specified conditional distributions (party conditional on race, gender, age and education; income conditional on education) chosen to resemble a US opt-in panel. Condition assignment: every profile appears in all 17 conditions (see D.3).
- **D.2 Profile verbalization** — which variables, rendered how (template vs generated narrative; if generated: model + prompt): Not verbalized. Profiles are numeric records; demographics act on responses through three latent traits (climate orientation, institutional trust, action propensity) and through partisan/education/age multipliers on treatment effects, all specified in `pipeline/priors.py`.
- **D.3 Assignment & weighting** — number of personas, assignment to conditions (your responsibility, all 17 conditions), reuse, weighting/matching: 4,000 profiles; each is simulated in all 17 conditions with common random numbers (the same latent traits, item noise and response-style draws, differing only in the treatment term), giving 4,000 rows per condition. This reuse is a variance-reduction choice: between-condition differences in the file reflect the modelled effects rather than draw-to-draw sampling noise. No weighting.

## J · Internal selection procedure
- **J.1 Design-space search †** — how the final pipeline was chosen: how many configurations tried, internal validation criterion, what data it ran against: Two simulator configurations. Configuration 1 (independent draws per condition, 2,000/intervention) was inspected for party shares, control means, donation/newsletter baselines and realized effect ordering; the model judged the party split too Democratic, donation and newsletter baselines too high, and sampling noise too large relative to the modelled effects. No data from this study were involved; the criterion was agreement between the simulation and the model's stated intentions.
